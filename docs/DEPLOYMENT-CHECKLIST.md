# چک‌لیست استقرار امن خانه‌گی

## قبل از هر استقرار

- [ ] یک backup قابل بازیابی و یک پروژه Supabase آزمایشی داشته باشید.
- [ ] migrationها را به ترتیب با Supabase CLI و migration history بررسی و اجرا کنید.
- [ ] نقش‌ها را از سمت سرور/داشبورد مورداعتماد تخصیص دهید؛ هیچ‌گاه به فرم یا کلاینت اجازه نوشتن در `user_roles` ندهید.
- [ ] RLS را با حساب anon، مشتری، staff، admin و super_admin جداگانه آزمایش کنید.
- [ ] پرداخت را غیرفعال نگه دارید تا درگاه انتخاب و تأیید سروری تراکنش با مبلغ و شناسه سفارش پیاده‌سازی و آزمایش شود.
- [ ] `VITE_USE_DEMO_DATA=false` فقط پس از آماده بودن کاتالوگ واقعی و migrationها تنظیم شود.
- [ ] `VITE_SUPABASE_URL` و `VITE_SUPABASE_ANON_KEY` تنها مقادیر عمومی فرانت‌اند هستند. کلید service role، کلید درگاه و توکن‌های خصوصی فقط در Secrets سمت سرور قرار بگیرند.
- [ ] دامنه واقعی را در `public/sitemap.xml` و metadata جایگزین کنید.
- [ ] آزمون‌های `npm test` و `npm run build` را در CI اجرا کنید.

## آزمون پذیرش حداقلی

1. در حالت واقعی، اگر view کاتالوگ خطا بدهد هیچ محصول دمو یا قیمت نمونه نباید نمایش داده شود.
2. مشتری عادی نتواند محصولات draft، سفارش کاربران دیگر، یا موجودی دقیق را بخواند.
3. مشتری نتواند نقش خود را تغییر دهد یا `payment_status` سفارش را از مرورگر به `paid` تغییر دهد.
4. دو سفارش هم‌زمان برای آخرین موجودی نباید باعث فروش بیش از موجودی شوند.
5. لغو سفارش پرداخت‌نشده باید رزرو را آزاد کند؛ پرداخت فقط پس از تأیید معتبر سرور باید موجودی را کم کند.
6. ایجاد محصول و موجودی اولیه یا هر دو موفق شود یا هر دو rollback شوند.
7. CSV با متن‌هایی که با `=`, `+`, `-` یا `@` شروع می‌شوند به‌عنوان فرمول قابل اجرا صادر نشود.

## وضعیت فعلی

این فهرست برنامه‌ی آزمون است، نه ادعای قبولی آزمون. درگاه پرداخت، ارسال، کوپن، واردسازی CSV و یکپارچه‌سازی رسمی ترب هنوز آماده بهره‌برداری نیستند.
